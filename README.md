# S-BFP: Complement results

We added complement experiments to assess the performance of S-BFP, implemented and evaluated the adaptive attacks as requested.

The experiment involved 19 participants. They are instructed to register and login on our test website. We also implemented a relay website and instructed the participants to login via the relay website.

## Organization of this Repo

`/complement_data` contains the logs of the replay and relay attack experiments, these logs are analyzed to produce the results.
`/complement_scripts` contains the scripts that can be used to reproduce the data in this report.
`/complement_result` stores the tables and data generated by the reproduction scripts.
`/rearrangement_emulation` contains the implementation of the naive replay and rearranged replay attack. Please refer to the `readme` file for instructions to run the attack.
`/relay_emulation` contains the implementation of the relay website. Please refer to the `readme` file for instructions to run the attack.

## Reproduction

From the repository root:

```sh
python -m complement_scripts.reproduce
```

The command prints all report tables and saves CSV tables and calculated data in [the results directory](complement_result). An existing output is backed up before replacement. Python's standard library is sufficient for report reproduction.

## Fingerprint acceptance

Login decisions use the final server result. A changed seed relative to enrollment is an expected-rejection context under the study protocol. Platform changes are used only when seed-linked metadata is available. Accepted means no 2FA will raise. We observe 3 rejected logins through the relay website. In these cases the participants tried to use a different device to login to their account through the relay website and is expected to be rejected.

## Relayed logins (Reviwer C-Q1, Reviwer D-Q2)

The relay website logs the session_ids of the relayed sessions. We use these markers to distinguish which sessions are relayed in the original websites assess logs. Relay markers contain 53 rows, matching 26 current sessions; 27 markers have no final event. Unmatched markers are not counted as failed logins. Unmarked sessions are classified as direct under the assumption that the marker list is complete; route is not inferred from latency.

Same-context relay acceptance and changed-context rejection are reported separately above. Expected changed-context failures are not evidence of relay detection. These are observational results, not a controlled estimate of relay resistance.

| experiment | mode | observation | attempts |
| --- | --- | --- | --- |
| recorded-position | rearranged | audio baseline hash mismatch | 41 |
| recorded-position | unchanged | audio upload rejected: Unexpected audio buffer length | 111 |

[CSV table](complement_result/replay_failure_observations.csv)

The recorded-position batch used 37 accounts with three attempts per mode. It reassigned saved Canvas rows to fresh positions and inserted fresh Audio silence gaps. Old and fresh challenge content differed in that batch.

Success means final authenticated login, not HTTP upload success. Infrastructure/setup errors are separate from completed attack rejections. A malformed replay upload that causes incomplete final verification remains a failed attack. Failure observations can overlap within one attempt. The experiments assume access to valid credentials, seeds and historical renderings; password acquisition is outside the measured procedure. The account batch used temporary test-password substitution, with restoration recorded in its historical audit. The current report does not repeat that procedure.

[Per-attempt outcomes](complement_result/replay_results.csv) and [per-account outcomes](complement_result/replay_users.csv) use the persistent anonymous account IDs stored directly in the source records.
